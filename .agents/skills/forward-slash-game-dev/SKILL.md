# forward-slash-game 开发流程

## 项目与规则来源

- 按 Phaser 4.1.0 + Vite、720×1280 竖屏和手机优先体验理解项目；依赖变化以实际 package.json 为准。
- 每次读取当前 AGENTS.md 及修改目录内适用的 AGENTS.md，不用聊天记忆代替现有实现。
- 在上级指令允许的范围内，以用户最新明确要求和当前 AGENTS.md 为准；历史方案、旧代码和旧文档不能覆盖最新确认。
- 让 AGENTS.md 保存权威玩法、具体设计和长期约束；让本 Skill 只保存开发流程与方法。不复制 AGENTS.md 全文，不在这里固化当前版本、波数、商品池或技能数值。
- 用户主要使用手机。默认由当前具备仓库权限的助手执行已授权任务，不要求用户操作电脑；无权限时说明阻塞，可提供完整的云端 Codex 指令，不声称能够控制其他 Codex 会话。

## 每次任务的执行顺序

1. 核对工作区、当前分支、最新 main 的 SHA、package.json、src/config/version.js 和相关目录结构；无法核实远端时明确说明。保护用户未提交修改。
2. 阅读需求直接涉及的实现和测试，确认调用链、数据来源及实际失败路径。先理解再修改，不凭猜测重写。
3. 开发前确定最小修改范围、验收点和本次检查清单，按实际依赖说明检查理由；简述本次改什么、不改什么。需求明确的小修改直接执行，不反复询问；只有规则不明、实质扩大范围或遇到权限阻塞时才询问。
4. 实施最小完整改动。一次只处理当前任务，优先不超过三个生产文件；确需超过时先解释。修 Bug 优先修根因，不用大范围调参数掩盖问题。
5. 执行下面的云端检查，审查实际 diff、边界行为和模式隔离。功能或修复按仓库约定同步版本及必要的版本断言；纯文档或 Skill 变动不擅自升级游戏版本。
6. 如实汇总修改、测试和未完成项，完成适用的提交与 PR 工作。不把创建 PR 当成验收完成。
7. 需要用户手机测试时，给出简短、具体的操作步骤及预期结果，不要求用户自行推导测试方法。

## 测试与手机验收

- 以用户最新确认的按任务范围验证为准；旧文档中“每次都跑全部验证”的要求不再作为默认流程。开发前确定检查清单，不能某项失败后临时删掉、改成可选或放宽有效断言。
- 游戏代码的小改动默认执行 `npm run build`、当前功能专项测试、直接受影响的回归和 `git diff --check`。从 package.json 和 scripts/ 选择真实存在的命令，不编造命令。
- 保留整套回归和整套浏览器脚本，供大版本、跨系统改动或用户明确要求时使用；不在每次小改动时自动运行。扩展检查范围须说明具体依赖或风险。
- 禁止主动执行、重跑或深入排查与当前任务无关的检查。不能因为全套脚本现成，就把专项验证接进整套脚本并连带运行无关项目。例如新增肉怪只检查肉怪行为、相关伤害/击退结算和生命周期清理，不因此重跑战士命中率、商店买卖或技能替换的整套浏览器流程。
- 仅改 Skill 或文档时，只检查 YAML frontmatter（如适用）、文件路径、内容一致性和 diff；不构建游戏、不运行游戏或浏览器测试、不要求用户手机验收。仅改验证工作流时检查语法、范围判断和直接受影响的 CI 行为。
- Skill 的文字不会自动改变 GitHub Actions。CI 应与事先确定的任务检查范围一致；若工作流仍无条件运行整套测试，明确说明配置尚未落实，不能声称已取消。获授权后单独调整触发范围，保留有效测试；不擅自绕过仓库实际必需门禁。
- 浏览器自动化仅在确有必要且能快速验证当前改动时执行专项场景。手机触控、真机手感、需人工观察的视觉效果及长时间重复游玩，云端不便或耗时明显过长时交给用户；不反复安装浏览器或跑大量对局来证明简单修改。
- 交接手机体验不等于已通过。给出至多几步操作：从哪里进入 → 做什么 → 观察什么 → 预期结果；需要反馈时说明截图、短录屏或现象即可，不要求桌面日志。
- 如实区分本次通过、本次新增失败、基线已有失败、环境受限、按范围未执行及仍待用户验收。已有失败须有基线证据；发现无关自动检查失败也要报告，不把失败说成通过，不擅自扩大当前任务修复。
- 本次适用检查或实际必需 CI 未完成、失败，或审查未完成时保持 Draft。少量样本或自动化通过不代表整局平衡完成。

## 游戏修改边界

- 保留用户已经确认的核心循环、UI、数值体系和流程；商店、技能、战斗具体规则查最新 AGENTS.md、当前任务及代码，不套用历史方案。
- 默认仅调整普通模式平衡，保留测试模式规则；共用 Bug 修复可覆盖两种模式，但不得夹带数值调整。
- 针对具体问题机制调整少数变量；不直接全局增加怪物生命，不随意削弱普攻或整体属性。明确预期收益和副作用，避免同时改多个体系导致无法判断原因。
- 让构筑明显影响战斗表现，不做固定唯一配方；保留合理随机混搭通关的可能。技能独立获得、独立有效，不强制特定前置组合。
- 涉及战斗回调时检查目标同步死亡或销毁；涉及技能移除、场景关闭和重启时检查事件、计时器、特效与引用清理。保留失败施法不无故消耗冷却等现有安全约束。
- 不顺手重构、改名或修复无关问题。发现其他问题可报告，不未经允许一起修改。

## Git 与 PR

- 新任务从最新 main 建立独立分支。原 PR 尚未合并时，同一任务的后续修复继续原分支与原 PR；已合并功能的新修改使用新分支、新 PR。
- 只提交本任务文件，保护其他工作；不擅自覆盖、重置或清理用户修改。游戏功能 PR 由用户最终合并；用户明确要求新增或更新的纯 Skill PR，可由助手完成适用检查和审查后直接合并。
- 提出“可以合并”前，完成适用的本地验证，审查实际 diff、base/head 和边界行为，确认 review threads 已处理，并核实事先确定的本次适用检查及仓库实际必需 CI 全部结束且通过；用户手机体验未完成时，明确列为后续验收，不冒充已通过。
- 本次适用检查失败、尚在运行、必要验证未执行或审查未完成，都不得说“可以合并”或把 PR 标为 Ready；保持 Draft 并明确阻塞原因。不能凭 GitHub 的合并按钮或推测基线问题跳过检查，也不能在失败后缩减原定范围。交付第一句明确“可以合并”或“暂不能合并及原因”，不要让用户追问。

## 完成后的汇报格式

【版本/分支】实际版本、分支及必要的 SHA；版本未变则注明。

【修改内容】改动文件、行为变化及原因。

【明确没有修改的内容】相关玩法、模式、数值或流程边界。

【测试结果】实际执行的命令与结果；失败、未执行和限制分别说明。

【需要用户手机验证的内容】简短操作、观察点与预期；无需则明确写无。

【提交/PR】实际提交、PR 链接及状态；未创建则说明。游戏功能 PR 不自动合并。
